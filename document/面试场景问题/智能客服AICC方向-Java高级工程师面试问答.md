### Q6. 讲讲一次完整的外呼流程，从系统发起呼叫到挂断。

**回答：**

一次外呼从系统侧看是这样的：

1. **任务下发**：外呼任务被拆成一个个呼叫任务，进入调度器；调度器按线路并发配额、客户所在地区的时间窗（避免骚扰）、重拨策略决定什么时候真正发号。
2. **呼叫发起**：平台通过 SIP 向运营商/中继网关发 `INVITE`，携带 SDP（我能接受的编码、RTP 端口、地址）。
3. **信令协商**：回 `100 Trying` → `180 Ringing`（对方振铃）→ 被叫摘机回 `200 OK` → 主叫发 `ACK`，会话建立。
4. **媒体建立**：按 SDP 协商结果走 RTP 传音频（一般是 PCMU/PCMA，即 G.711，或 Opus），RTCP 做质量反馈。
5. **业务处理**：接通后分两条路——走 IVR/AI 机器人（音频流送 ASR，LLM 生成回复，TTS 播回）或转人工（CTI 分配坐席，桥接媒体）。
6. **挂断**：任一方发 `BYE`，对端回 `200 OK`，会话结束；平台生成话单（CDR：主被叫、起呼时间、接通时间、挂断时间、挂断方、挂断原因码、录音文件 ID）。
7. **后处理**：录音落存储 → ASR 转写 → 质检 / 打标 / 进入 CRM 工单。

**系统侧的关键难点**：一是**状态机必须能容忍事件丢失**（比如 BYE 丢了，要靠 RTP 静默超时或 SIP 会话定时器 Session Timer 兜底判断挂机）；二是**计费/话单以哪个时间点为准**（一般是 200 OK 而非 180）；三是**未接通的失败码要分类处理**（486 忙、480 暂时不可用、408 超时、404 空号、603 拒接），不同码决定不同的重拨策略。

> **加分点**：说出"SIP 是信令、RTP 是媒体，两者分离，所以可能出现**信令通了但媒体不通（单通/无声）**，这类问题只能靠 RTCP 统计或 ASR 侧能量检测发现"——这是只有做过的人才知道的细节，说出来面试官会明显高看你。

### Q7. SIP 和 RTP 分别是什么？为什么分开？

**回答：**

SIP（Session Initiation Protocol）是**信令协议**，负责建立、修改、终止会话，文本协议类似 HTTP，一般走 UDP 5060 / TCP 5060 / TLS 5061。它只协商"我们要不要通话、用什么编码、媒体发到哪个 IP 端口"，不传语音。

RTP（Real-time Transport Protocol）是**媒体传输协议**，走 UDP，真正承载编码后的音频包，带序列号和时间戳用于抖动缓冲和乱序重排；RTCP 是它的控制伴生协议，回传丢包率、抖动、往返时延，用于质量监控和自适应。

**分开的原因**：信令需要可靠、可路由、可经过代理和鉴权（所以可以走 TCP/TLS），媒体要低延迟、容忍少量丢包（所以走 UDP）。两者生命周期不同——媒体路径可能经过 SBC/媒体服务器中继，而信令可能经过一串 Proxy。分开后可以独立扩展：信令服务器处理高并发短事务，媒体服务器处理长时有状态的流。

**工程上的三个坑**：
1. **NAT/私网地址**：SDP 里带的是终端内网地址，媒体到不了 → 需要 SBC 或 rtpengine/rtpproxy 做媒体中继，或 ICE 打洞；
2. **单通问题**：信令 200 OK 了但 RTP 单向不通，用户听到静音 → 要监控 RTCP 的收发包计数；
3. **编解码不匹配**：一端 G.729 一端 G.711 需要转码，转码消耗 CPU 且增加延迟 → 尽量透传同编码。

### Q8. 常见的 SIP 状态码有哪些？在业务上怎么用？

**回答：**

- **1xx 临时响应**：100 Trying（收到，正在转）、180 Ringing（振铃）、183 Session Progress（带早期媒体，比如彩铃）。
- **2xx 成功**：200 OK（摘机/成功）。
- **3xx 重定向**：302 Moved Temporarily。
- **4xx 请求失败**：
  - 401/407：需要认证（digest 挑战）
  - 403 Forbidden：被拒（黑名单/无权限）
  - **404 Not Found**：号码不存在 → **空号，直接标记不可达，不再重拨**
  - 408 Request Timeout：超时未响应
  - **480 Temporarily Unavailable**：暂时不可用（关机/不在服务区）→ **可重拨**
  - **486 Busy Here**：占线 → **延迟重拨，退避**
  - 487 Request Terminated：主叫取消（常用于预测式外呼放弃呼叫）
- **5xx 服务器错误**：503 Service Unavailable → **线路/中继故障，熔断该线路，切换备用**
- **6xx 全局失败**：603 Decline（拒接）、604 Does Not Exist Anywhere → **空号**

**业务用法**：我们把这些码建成"**可重拨矩阵**"——按码分类（永久失败/暂时失败/线路故障），分别映射到：停止外呼、N 次退避重拨（如 1min/10min/1h/次日）、切换中继线路。同时用这些码算**接通率**和**号码质量分**，喂给预测式外呼的放号算法。

> **加分点**：提一句"预测式外呼会出现**接通但坐席已占满**的情况，这时主叫侧要主动发 CANCEL/487 挂掉，但这类'放弃呼叫'在合规上有严格比例限制（一般 abandon rate 要控制在 3% 以内）"——合规意识是加分项。

### Q9. CTI、ACD、IVR 分别是什么？和后端系统的边界在哪？

**回答：**

- **CTI（Computer Telephony Integration）**：把电话系统和计算机系统连起来的中间层。对我们后端来说，CTI 提供的是**呼叫控制 API**：发起呼叫、挂断、保持、转接、会议、静音、播放语音、录音控制，以及**坐席状态管理**（签入、示闲、示忙、通话中、话后处理 Wrap-up、签出）。后端通过 CTI 的 API 或事件回调驱动业务。
- **ACD（Automatic Call Distribution）**：自动呼叫分配，负责把来话/外呼接通后的会话分配给合适的坐席，包括**技能组路由、排队、优先级（VIP 优先、最长等待优先）、溢出（超时转到另一个组）、排队播报**。
- **IVR（Interactive Voice Response）**：交互式语音应答，按键菜单/语音导航，现在 AI 化的 IVR 就是 ASR+LLM+TTS 的对话机器人。

**边界划分（这题真正考的是这个）**：
- 语音平台（FreeSWITCH/呼叫中心平台）负责**媒体和信令**，它是有状态的、长连接的；
- **后端负责业务与决策**：客户画像、号码名单、任务调度、路由规则、话术/知识库、ASR/TTS/LLM 的编排、话单与质检。
- 两者通过**事件 + 命令**解耦：平台把呼叫事件（RING/ANSWER/HANGUP/DTMF）通过 MQ 或 WebSocket/HTTP 回调推给后端，后端通过 ESL/HTTP API 下命令。

**关键设计原则**：后端**不能假设事件一定到、一定有序**，所以要（a）事件带唯一 callId + 序号做去重和乱序处理；（b）呼叫做**超时兜底**——比如发起呼叫后 60s 没收到 ANSWER 事件，主动查一次平台状态；挂断事件丢失时靠 SIP Session Timer 或媒体静默兜底。这正是我在 AIPhone 治理 Azure 回调超时/无回调时做的事：把判定从业务侧上移到模型侧，业务侧再做一次决策兜底。

### Q10. 坐席状态机怎么设计？技能组和排队怎么实现？

**回答：**

**坐席状态机**（这是后端核心模型之一）：
```
OFFLINE(签出) → LOGIN(签入) → IDLE(示闲)
IDLE → RINGING(振铃/预占) → TALKING(通话中)
TALKING → WRAPUP(话后处理，填工单/打标) → IDLE
任意 → BUSY(示忙：培训/休息) → IDLE
异常 → FORCED_LOGOUT(强制签出)
```
设计要点：
- **状态变更必须幂等 + 带版本号**（乐观锁），因为 CTI 事件和后端操作可能并发修改；
- **预占机制**：分配坐席时先"预占"，避免两个呼叫分到同一个坐席（用 Redis SETNX + 过期时间做席位锁）；
- **话后处理超时自动转示闲**，防止坐席忘记点"完成"导致席位泄漏——这是外呼系统最常见的可用性事故之一；
- 状态流转落**坐席状态流水表**，用于工时统计、接通率分析、SLA 考核。

**技能组与排队**：
- 坐席有**技能标签**（业务线、语言、等级），坐席可属于多个技能组，组有**优先级权重**；
- 分配算法一般多级：**先筛技能匹配的坐席池** → **按策略排序**（最长空闲优先 LIFO 让熟练度高的人接、或最长等待优先 FIFO 保证公平）→ **考虑负载和技能等级**；
- 排队：用**优先级队列**（VIP 权重 + 等待时长动态提权，防止饿死），队列超时或超长则**溢出**到备用组、转 IVR 留言、或触发回呼；
- 实现上：Redis 存坐席池和席位锁，排队用延迟队列 + 定时扫描兜底，分配决策在内存中完成（毫秒级），分配结果异步落库。

> **加分点**：提一句"**排队时长预估**——根据当前队列长度、坐席数、平均通话时长（AHT）估算等待时间播报给用户，这个 AHT 要用滑动窗口实时算，不能取历史均值"。

### Q11. AI 转人工怎么设计？转过去的信息怎么保证不丢？

**回答（这是本岗位最高频的场景题）：**

**触发**：三类信号——（1）LLM 意图识别命中"转人工"；（2）规则触发：同一问题重复 N 次、负面情绪检测、关键词（"投诉""我要人工"）、静默超时；（3）业务节点：下单、支付等关键动作需要人工确认。

**流程**：
1. 决策层决定转人工 → 生成一个**转接单**，包含：callId、客户 ID、**会话上下文**（已收集的槽位/字段）、**AI 对话摘要**（由 LLM 实时生成，控制在 200 字）、命中意图、情绪分、建议技能组、录音/转写 ID；
2. 写一条转接记录（状态 INIT），保证**先落库再转接**，防止转接成功但上下文丢失；
3. 调用 CTI 的转接接口（FreeSWITCH 里是 `uuid_transfer` 或 `uuid_bridge`），把呼叫转到目标技能组；
4. 坐席侧**弹屏（Screen Pop）**：坐席接起的同时，工作台通过 callId 拉到客户画像 + **AI 摘要 + 对话转写**，坐席 3 秒内知道客户要什么，避免让客户复述；
5. 转接结果回写（成功/失败/无人接听），失败则回到机器人或进队列排队。

**可靠性要点**：
- **桥接优先于二次外呼**：尽量用 `uuid_bridge`/REFER 保持同一通电话桥接，避免挂断再呼（客户体验断裂且多一次呼叫费用）；
- **转接超时兜底**：发起转接后 N 秒没收到坐席应答事件，主动查状态，失败则回滚到机器人继续对话，不能让客户听到静音；
- **上下文只传引用不传大对象**：摘要和转写存 DB/对象存储，转接单只带 ID，避免 MQ 消息膨胀；
- **幂等**：转接请求带唯一 transferId，CTI 重复回调不重复创建工单。

> **加分点**：加一句"我还会做**转人工率归因**——把转人工按原因打标（AI 答不上/客户情绪/业务流程要求/ASR 识别错误），反哺到知识库和话术，这个闭环才是 AI 外呼能持续提效的关键"。

### Q12. 预测式外呼（Predictive Dialer）了解吗？为什么它是最难的？

**回答：**

三种基本外呼模式：
- **预览式（Preview）**：先把客户资料推给坐席，坐席确认后系统才拨号——体验最好、坐席效率最低；
- **渐进式（Progressive / Power）**：坐席空闲时才拨一个号，1:1，无放弃呼叫，坐席效率中等；
- **预测式（Predictive）**：不等坐席空闲，**按算法预测"多久后有坐席空出来"提前批量放号**，坐席效率最高，但会出现"接通了但没坐席"的**放弃呼叫（Abandoned Call）**。

**为什么难**：这是一个**在合规约束下的吞吐优化问题**。核心变量：接通率 p、平均振铃时长、平均通话时长 AHT、坐席空闲数。放号速率要动态算：`并发放号数 ≈ 空闲坐席数 / 接通率 × 放大系数`，并且要用滑动窗口实时更新 p 和 AHT。放多了 → abandon rate 超 3% 违规且体验差；放少了 → 坐席空等，成本高。

**系统实现**：
- 放号速率由**控制器**动态调节（类似 TCP 拥塞控制：慢启动 + AIMD），实时监测 abandon rate 和坐席空闲率的平衡点；
- 用**令牌桶**限制每秒放号数，令牌按线路并发上限和客户时间窗发放；
- 接通但无坐席时，走**降级策略**：先播"请稍候"进队列（有坐席立刻接）→ 超时则礼貌挂断并标记"需回呼"；
- 号码去重（同一客户在冷却期内不重复呼）、频次控制（日/周上限）、黑名单和 DNC（Do Not Call）名单过滤。

> **加分点**：把它类比成"DSP 实时竞价的预算消耗控制"——在给定预算/配额约束下最大化有效转化，我在 DSP 平台做过类似的控制逻辑。这个类比是简历里真实可讲的连接点。

### Q13. FreeSWITCH / OpenSIPS / Kamailio / Asterisk 这些你了解哪些？

**回答（诚实版 + 展示学习深度）：**

我实际生产环境用的是云厂商的 ASR/TTS 服务和自研的流式编排，没有亲手搭过 FreeSWITCH 集群，所以我先说清边界。但我梳理过它们的分工：

- **FreeSWITCH**：软交换 + **媒体服务器**（B2BUA），既能处理 SIP 信令也能处理媒体（放音、录音、会议、转码）。核心是 `mod_sofia`（SIP）、`mod_callcenter`（**ACD 队列/技能组**，含 tier/agent 配置和分配策略）、`mod_conference`、`mod_unimrcp`（**MRCPv2 客户端，用来对接 ASR/TTS 引擎**）、`mod_httapi`/`mod_vlc`、`record_session`、`uuid_bridge`。对外控制接口是 **ESL（Event Socket Library）**，有 inbound（我连它）和 outbound（它连我的脚本）两种模式，我们后端就是订阅 ESL 事件、下发 originate/transfer/hangup 命令。
- **Kamailio / OpenSIPS**：纯 **SIP 信令代理**（Proxy/Registrar），不碰媒体，走 stateless/stateful 转发，单机能扛非常高的 CPS（每秒呼叫数），用于注册、路由、负载均衡、防攻击，通常**和 FreeSWITCH/Asterisk 配合**：Kamailio 做信令入口和分发，媒体服务器做媒体。
- **Asterisk**：更偏 PBX/IP-PBX，生态成熟，通道和拨号计划（dialplan）模型。
- **SBC（Session Border Controller）**：部署在边界，做 **NAT 穿透、媒体中继、拓扑隐藏、协议归一化、安全防欺诈、QoS 和编解码转码**。公网运营商对接基本都要过 SBC。
- **MRCPv2**：ASR/TTS 的标准协议，媒体服务器通过 MRCP 控制识别引擎，音频走 RTP。

所以如果让我接手，我理解的正确架构是：**SBC/运营商中继 → Kamailio/OpenSIPS（信令分发）→ FreeSWITCH（媒体 + ACD）→ 后端业务系统（ESL 事件 + API 编排 AI 与业务）**。

> **注意**：这题如果答不上来，至少说出"SIP 信令与 RTP 媒体分离"和"B2BUA vs Proxy 的区别"，能救回一部分。

### Q14. 通话录音和质检系统怎么设计？

**回答：**

**录音链路**：
- 在媒体服务器侧 `record_session` 录音，一般录**双轨（stereo）**，坐席和客户各占一个声道，方便后续**说话人分离**；或混合单轨 + 依赖 ASR 的 speaker diarization；
- 录音文件流式写入对象存储（OSS/S3），元数据（callId、主被叫、时长、文件 URL）落 MySQL/ES；
- **录音落盘必须可靠**：先写临时文件 → 校验时长和大小 → 转存对象存储 → 回写状态，失败要有补偿任务重录或标记"录音缺失"告警（合规要求：金融/保险类外呼录音是强留痕要求，保存期通常 3-5 年）。

**质检链路**：
1. 录音 → ASR 转写（**带说话人标签和时间戳**）→ 文本落 ES/ClickHouse；
2. **规则引擎**：关键词命中（禁用语、承诺性用语）、静默时长、抢话/打断次数、语速、通话时长、开场白/结束语是否规范；
3. **大模型质检**：按质检模板打分（服务态度/合规/业务准确度/问题解决率），输出分数 + 命中项 + 证据片段（引用原文）；
4. 规则结果和大模型结果**加权融合**，低分或高风险（合规项）进人工复核队列；
5. 质检结果反哺：命中高频问题 → 更新知识库/话术；坐席维度聚合 → 培训和绩效。

**工程要点**：质检是**离线批处理 + 准实时**混合，用 MQ 削峰（通话高峰集中在白天），大模型调用要**限流 + 缓存 + 降级**（预算控制），同样的话术片段做结果缓存复用。这里我在 AIPhone 做过类似的事——用置信度前置判定减少大模型调用，成本降 30%，这个思路可以直接搬过来。

> **加分点**：提"**实时质检/实时辅助**"——通话中就把 ASR 文本实时送规则和大模型，命中风险时**实时弹屏提醒坐席**甚至提醒组长介入，这是从"事后质检"到"事中干预"的升级，也是现在很多 AICC 产品在卷的点。

### Q15. 呼叫并发量怎么评估？"1000 并发通话"意味着什么？

**回答：**

要拆开算，不能用"并发数"一个数字拍脑袋：

- **并发通话数（Concurrent Calls）**：同时存在的通话路数。1000 并发 G.711（64kbps，20ms 打包）≈ 单向 64k + 包头开销，实际每路约 80-90kbps，1000 路 ≈ **90 Mbps** 带宽（双向翻倍）。
- **CPS（Calls Per Second）**：每秒新建呼叫数，决定**信令侧**压力。1000 并发 + 平均通话 3 分钟 → 稳态 CPS ≈ 5.6；但实际放号是波形的，峰值可能是稳态的 3-5 倍，且外呼是**批量突发**的，所以信令侧按峰值 CPS 设计。
- **坐席并发**：坐席数由并发通话和 AHT 决定：`坐席数 ≈ 并发数 × 占用率`。
- **应用服务器压力**：每通电话的**信令事件**（Ring/Answer/Hangup/DTMF）很少（每通几个到几十个），真正的压力在 **ASR/TTS 的流式长连接**和 LLM 调用——所以 AI 外呼的瓶颈通常不在呼叫控制，而在 **AI 服务的并发连接数和 RT**。

**设计上**：
- 呼叫控制服务按 **CPS × 单通事件数** 估算 QPS，做水平扩容；
- AI 编排服务按**并发连接数**估算（长连接内存和线程开销），Netty 单机可扛万级并发连接，但要控制每个连接的 ByteBuf 内存；
- 媒体服务器按**并发路数 + 转码 CPU**估算，转码最贵，尽量同编码透传；
- 全链路要**压测**：压测要模拟真实波形（突发放号），而不是匀速。

> **加分点**：提"容量评估三件套：压测 + 监控 + 水位预警，且容量要有**红线**——并发达到线路上限的 80% 就开始限流放号，不能打满"。

## 4. AI 语音链路题（**这是你的主场，必须打得漂亮**）

### Q16. 讲讲实时语音对话链路的端到端延迟怎么拆解和优化？

**回答（用你的真实项目讲）：**

在 AIPhone 电话同传里，端到端 RT 拆成几段：
1. **音频采集与上行传输**（设备→服务端）；
2. **VAD 端点检测**（判断一句话说完了没）；
3. **ASR 流式识别**（含模型侧返回首字/终句的时间）；
4. **后处理与决策**（置信度判定、语言判定、是否要送大模型）；
5. **LLM 生成**（首 token 延迟 + 流式输出）；
6. **TTS 合成**（首包延迟）；
7. **下行播放**。

**我做的优化**：
- **决策前置**：不再把每个 ASR 句子都丢给大模型，而是先用**文本置信度 + whisper 语言置信度**做前置过滤，只有置信度不足或语义存疑时才调用大模型兜底。结果是**处理 RT 平均降 40%、大模型调用费用降 30%、转录删除率从 30% 降到 10%**。这里的关键认知是：**大模型是准确性的兜底手段，不是每一句的默认路径**，用便宜的确定性规则挡掉 80% 的请求，大模型只处理难的那 20%。
- **异步化**：语言检测走异步旁路，不阻塞主链路文本透出。
- **流式而非串行**：ASR 出中间结果就开始准备下游，而不是等终句；TTS 边合成边播放。
- **超时兜底**：模型回调超时/无回调时用超时断句强制结束句子，避免用户一直等。

**到 AICC 场景的迁移**：智能外呼的 AI 对话延迟容忍度比同传高（人对答有自然停顿），但同样可以做**分级处理**——高频标准话术走缓存/模板直接命中，只有未命中的才走 LLM，并且用**流式首 token**让用户在 300-500ms 内听到声音（可以先播一个"嗯，您说的是…"的 filler 音），体验会好很多。

### Q17. 双路 ASR 是怎么回事？为什么这么做？（**招牌题**）

**回答：**

**问题背景**：单路 ASR 在噪声环境、口音、短句场景下**幻听严重**——模型把噪声或别人的话识别成内容。在同传里，幻听的句子会被翻译后 TTS 播给对方，体验是灾难性的；在智能客服里，幻听会导致**意图识别错误、错误答复、甚至错误下单**。

**方案**：同一段音频并发送两路 ASR（不同供应商/不同模型，比如一路云厂商实时 ASR、一路 Whisper 类模型），拿到两组结果后做**仲裁决策**：
1. **文本置信度对比**：两路都给出置信度，取高者；
2. **语言置信度**：用 whisper 的语言置信度判断这段是否真的是目标语种（非目标语种基本就是幻听）；
3. **两路一致性**：两路结果文本相似度高 → 采信；差异大 → 进入仲裁；
4. **大模型上下文语义兜底**：把候选句子连同上下文给大模型，判断它是否符合语境，符合才透出；
5. **决策输出**：最终只透出胜出的一句，并按决策结果记账（用于后续模型迭代和问题归因）。

**工程难点**：
- **延迟**：两路并行不增加延迟（取先到的 + 仲裁窗口），仲裁窗口要短（比如 200-300ms），超时就按单路置信度放行，不能为了仲裁牺牲 RT；
- **成本**：双路识别成本翻倍，所以要做**分级**——安静环境/高置信度时用单路，检测到环境差（信噪比低、连续低置信度）才动态开双路；
- **可观测**：每一句的仲裁过程要落日志（两路原文、置信度、决策原因），这是后续优化模型和分析 bad case 的唯一依据。我做的时候把这套日志做成了质量分析平台，运营可以直接看 bad case。

**效果**：幻听错误文本透出减少 20%，转录删除率 30%→10%。

> **面试官可能的追问与回答**：
> - **"为什么不训练/微调一个更好的 ASR？"** → 短期成本高、周期长，双路 + 仲裁是**工程上可快速落地且可量化**的方案；而且它是**通用的容灾架构**——任何一路供应商挂了或降级，另一路能顶上，这对生产系统很重要（对应岗位要求的"故障隔离和降级策略"）。
> - **"双路结果不一致时以谁为准？"** → 不固定以谁为准，按置信度 + 语言置信度 + 上下文语义加权投票；同时做**历史统计**——统计各供应商在不同场景（方言、噪声、行业术语）的准确率，做**场景化路由**（比如粤语场景优先 A，普通话标准场景优先 B）。这个可以讲成"ASR 引擎路由层"，是平台化能力。

### Q18. ASR 流式回调超时/无回调怎么治理？（**招牌题 2**）

**回答：**

这是我在 AIPhone 作为负责人解决的、影响面最大的一个问题。

**现象**：Azure ASR 的 `Recognized` 事件（一句话识别完成）会出现**超时才回调**或**根本不回调**两种情况。后果是两种：
- 回调**超时**：用户已经说了下一句，上一句才回调上来，造成**多句子合并透出**，用户看到一串不该在一起的文本；
- **无回调**：句子一直悬着，流式中间结果（幻听内容）持续透出，用户看到不断变化的错误文本。

**定位过程**：
1. 先从**数据**入手而不是猜——把回调时间、句子时长、音频能量、是否连续说话做关联分析，量化影响面（每天多少句受影响）；
2. 定位到根因在**模型侧的断句策略**与**网络/流式会话状态**的组合，单纯在业务侧加超时阈值只能缓解，不能根治，且阈值调大调小都有副作用（调大延迟高，调小误截断）。

**方案（架构层面）**：推动把**超时断句的判定从业务侧上移到模型侧**，同时业务侧保留**决策权**，形成"**模型侧判定 + 业务侧决策**"的双层架构：
- 模型侧：根据音频特征和自己的内部状态判定这句话已经结束，主动触发断句回调；
- 业务侧：收到回调后做二次决策（置信度、语言、上下文、去重），并按自己的超时兜底强制收句，两边取**先发生者**，保证任何情况下句子都会被结束，不会悬着。

**推动过程**：这个改动跨了模型侧和业务侧，我组织了原方案设计同事、组长、模型侧同事和 CTO 做技术方案评审，把影响面数据、两种方案的对比、灰度计划讲清楚后才落地。

**结果**：重复透出减少 500+ 次/天，幻听流式文本减少 1000+ 次/天。

**到 AICC 的迁移**：这个模式对呼叫系统是完全同构的——**SIP/RTP 的事件同样会超时和丢失**（BYE 丢了、ANSWER 事件没推）。我的做法一致：**不信任单一事件源，用状态机 + 超时兜底 + 主动状态查询对账**。这也是我在设计任何异步链路时的默认习惯：先落库、事件幂等、超时补偿、主动对账。

> **加分点**：这题要强调**组织能力**——跨团队推动架构改动、拉评审、拿数据说服人，正好对应岗位第 6/8/10 条。

### Q19. VAD 是什么？怎么用？有哪些坑？

**回答：**

VAD（Voice Activity Detection，语音活动检测）判断音频里"哪里有人在说话、哪里是静音"。它在实时语音系统里三个作用：
1. **端点检测（断句）**：判断用户说完了没，触发送 ASR 或结束句子；
2. **省资源**：静音段不送 ASR，省算力和成本（直接对应我在 AIPhone 做的成本优化）；
3. **交互体验**：支持 **barge-in（用户打断机器人）**——检测到用户开口就立刻停掉 TTS 播放。

**坑**：
- **静音阈值和尾音**：阈值太激进会**截断**用户尾字（"我要退货…"被切成"我要退"），所以要有**尾音保护**（结束前留 200-400ms 静音缓冲）；太保守则延迟高；
- **噪声环境误判**：环境噪声、回声、对方串音会让 VAD 一直认为有人在说话 → 需要**回声消除（AEC）**前置，外呼场景尤其重要（TTS 播放的声音会被自己的麦克风收进去，形成回声，导致 ASR 把机器人自己说的话识别成客户说的）；
- **短停顿 vs 说完了**：人在句中会停顿，单纯静音时长不够，要结合**语义完整性**（标点预测、句末语气）；
- **音频质量差**：上行音频质量差时 VAD 和 ASR 都会失效，我在 AIPhone 做过**上行音频质量差提醒用户**的检测和引导，这个在智能外呼里同样有价值——客户听不清/环境吵时，与其硬识别，不如让机器人主动说"您那边有点吵，能换个安静的地方吗"。

> **加分点**：AEC（回声消除）是外呼系统必踩的坑，说出来很加分。

### Q20. ASR 在客服场景有哪些典型的准确率问题？怎么系统性提升？

**回答：**

**典型问题**：
1. **领域词/专有名词识别差**：产品名、订单号、人名、地名、行业术语。解决：**热词/类偏置（biasing）**——给 ASR 引擎注入业务词表（产品名、品牌名、常见姓氏），大部分云厂商支持 hotword/context 权重；
2. **数字和字母串**：手机号、验证码、金额、身份证号容易错。解决：**后处理正则校正** + **业务规则校验**（手机号 11 位校验、金额合理性校验）+ **重复确认话术**（"您的手机号是 138xxxx，对吗？"）；
3. **方言和口音**：解决：选择支持方言的模型或做**语种/方言路由**，我在 AIPhone 做过的"语言置信度 + 语种路由"就是这个思路；
4. **噪声/串音/回声**：AEC + 降噪 + 音频质量检测 + 主动引导用户；
5. **说话人混淆**：坐席和客户混在一起 → 双轨录音或 diarization。

**系统性提升（平台化思路，对应岗位第 7 条）**：
- **多引擎路由层**：抽象统一的 ASR 接口，按场景（语种/方言/行业/安静度）路由到不同引擎，支持**主备切换和灰度**；
- **识别质量可观测**：记录每句的置信度、引擎、耗时、最终结果是否被下游采纳、是否被用户纠正（用户说"不是，我说的是X"就是最强负样本）；
- **bad case 闭环**：质量分析平台 → 归因（引擎/热词/噪声/断句）→ 采取动作（加热词/换引擎/调断句参数）→ 效果回归；
- **成本与准确率权衡**：不是所有场景都要最高精度，做**分级**——简单确认句用便宜引擎，关键句（金额、地址确认）用高精度 + 人工复核。

这套思路我在 AIPhone 落地过："双路 ASR + 置信度仲裁 + 大模型兜底 + 质量分析平台"，正好是一套完整的 ASR 治理闭环。

### Q21. LLM 在智能客服里怎么用？怎么控制成本和延迟？

**回答：**

**用法分层**（不是所有问题都给大模型）：
- **L0 规则/模板**：高频标准问答、按键导航、固定话术 → 模板命中，零延迟零成本；
- **L1 小模型/缓存**：意图分类、情绪判断、关键词抽取 → 用轻量模型或缓存（相似问法向量召回命中历史答案）；
- **L2 大模型**：开放域问答、多轮对话、复杂意图、摘要生成、质检评分 → 走 LLM + RAG。

**成本控制**（我有实战数据：大模型调用费用降低 30%）：
1. **前置过滤**：置信度高的、规则能判定的，坚决不调大模型。这是最大头；
2. **缓存**：（a）**精确缓存**——相同问题直接返回；（b）**语义缓存**——向量相似度 > 阈值复用历史答案；
3. **分级模型**：简单任务用便宜的小模型，只有复杂任务用大模型；
4. **上下文裁剪**：不要每次都塞全量对话，用**滚动摘要**压缩历史；
5. **并发与配额**：按业务线设预算和 QPS 配额，超限降级到模板话术；
6. **批量离线化**：质检、话术挖掘、通话摘要这些**非实时**任务全部走离线批处理，削峰填谷，离线批量调用通常有更低价折扣。

**延迟控制**：流式输出 + 首 token 优先（先播 filler 音占位）+ 并行准备（ASR 出中间结果就预取知识库）+ 超时降级（LLM 超时立即切模板话术，绝不让用户等空白）。

**可靠性**：LLM 是外部依赖，必须**熔断 + 降级 + 兜底话术**，且输出要有**结构化校验**（JSON schema 校验、槽位合法性校验）和**安全过滤**（防 prompt 注入——客户说的话里可能有诱导性内容；防敏感信息泄露）。

> **加分点**：提 **RAG 知识库**建设——文档切分、向量化、混合检索（向量 + 关键词 BM25）、重排序（rerank）、引用溯源（回答必须带知识来源，便于客服核查），以及知识库的**更新与灰度**（新知识先在小流量验证准确率）。

### Q22. 智能质检和话术推荐怎么做？

**回答：**

**智能质检**（见 Q14，这里补充架构）：
- 数据：录音 → ASR 转写（带说话人和时间戳）→ 结构化文本落 ClickHouse/ES（ClickHouse 适合做大规模聚合分析）；
- 引擎：**规则引擎**（确定性强、可解释、用于合规红线）+ **大模型评分**（覆盖语义层、灵活度高）双引擎，结果加权；
- 输出：分数 + 命中项 + **证据片段（引用原文和时间点）** + 改进建议；
- 闭环：人工复核队列 → 申诉与校准（用人工复核结果反哺模型阈值）→ 坐席培训 → 知识库更新。

**话术推荐（实时辅助）**：
- 通话中实时取 ASR 文本 → 检索知识库（RAG）→ 召回 top-N 话术 → 重排序 → 推送到坐席工作台；
- 触发方式：**主动推荐**（识别到客户问题/异议自动弹话术）+ **主动触发**（坐席点"推荐话术"）；
- 关键指标：**采纳率**。这是唯一有效的度量——推荐了坐席不用等于没做。所以要按采纳率迭代召回策略，并做 A/B 实验；
- 冷启动：从**历史优秀坐席的实际话术**中挖掘（客服行业里叫 "best practice 挖掘"），这比人工编写话术库效率高得多。

我在 AIPhone 做的"电话同传信息交换知识库建设"和"同传质量分析提效平台"，本质上就是这套东西：知识库 + 质量分析平台的组合。

### Q23. AI 外呼 vs 人工外呼，系统设计的差异是什么？

**回答：**

| 维度 | 人工外呼 | AI 外呼 |
|---|---|---|
| 瓶颈资源 | **坐席工时**（最贵） | **AI 服务并发与成本**（ASR/TTS/LLM） |
| 并发模型 | 受坐席数硬限制，需预测式放号匹配坐席空闲 | 几乎无限并发，瓶颈在**线路并发上限**和 AI 服务配额 |
| 放弃呼叫 | 必须严控（合规） | 不存在（机器人永远能接），但**号码资源消耗**和**投诉风险**仍在 |
| 状态机 | 呼叫 + 坐席双状态机 | 呼叫 + **对话状态机**（多轮槽位填充） |
| 关键指标 | 接通率、AHT、成单率、坐席利用率 | 接通率、**AI 解决率**、意图识别准确率、**转人工率**、单通成本 |
| 失败处理 | 重拨策略 | 重拨策略 + **对话失败重试**（换话术、换时间、换通道） |

**核心差异**：AI 外呼的调度从"匹配坐席产能"变成"**匹配 AI 服务容量 + 控制成本 + 控制投诉风险**"。同时多了**对话质量治理**这条线：意图准确率、答非所问率、转人工率，需要一套完整的 bad case 闭环。

**混合模式是终态**：AI 先拨、筛选意向、分级（A/B/C 类意向），高意向**实时转人工**，这也是岗位 JD 里"AI 转人工"的核心价值——用 AI 的并发能力做筛选，把昂贵的人工工时花在最高价值的客户上。

## 5. 高并发与任务调度（岗位第 4 条，硬考点）

### Q24. 千万级外呼任务怎么调度？

**回答（系统设计题，见 Q45 的完整版，这里是要点）：**

分层设计：
1. **任务层**：任务（Campaign）→ 批次（Batch）→ 呼叫任务（CallTask）。任务入库时分片（按客户 ID 哈希分片），避免单点。
2. **调度层**：
   - **时间窗调度**：只在允许的时段（合规：一般 8:00-21:00）和客户所在地时区放号 → 用**延迟消息**（RocketMQ 延迟消息/时间轮）把任务投放到目标时刻；
   - **速率控制**：令牌桶限制每秒放号数，令牌按**线路并发配额**发放；多线路时做**加权路由 + 熔断**（某线路失败率超阈值切走）；
   - **优先级**：按客户价值/意向分级（A 类优先），用优先级队列，但要防低优先级**饿死**（等待时长动态提权）。
3. **执行层**：调度器只负责"决定发哪个号"，真正发号交给**无状态的执行器集群**，执行器通过 MQ 或分片拉取任务，水平扩容。
4. **状态层**：每个 CallTask 有明确状态机（PENDING→SCHEDULED→DIALING→RINGING→ANSWERED→TALKING→HANGUP→FINISHED/RETRY/FAILED），所有流转**事件驱动 + 幂等 + 版本号**。
5. **兜底层**：**超时扫描**（DIALING 超过 N 秒无事件 → 主动查平台状态）+ **重拨策略**（按失败码退避，最多 N 次）+ **去重**（同一客户冷却期内只呼一次）。

**容量**：千万级/天 ≈ 按 10 小时窗口算，平均 280 QPS，但外呼是突发的，峰值按 3-5 倍设计，即 1000-1500 QPS 的调度吞吐——这个量级用 MQ + 无状态执行器完全可控，**真正的瓶颈永远在运营商线路的并发上限，所以调度器本质上是一个"受限资源的多队列配额调度器"**。

> **加分点**：把"受限资源的配额调度"类比到 DSP 广告投放——预算（并发配额）+ 频控（号码频次）+ 竞价（线路成本择优），我在 DSP 平台做过类似控制。

### Q25. 限流怎么做？单机和集群限流有什么区别？

**回答：**

**算法**：
- **固定窗口**：简单但有临界突刺（窗口交界处两倍流量）；
- **滑动窗口**（Sentinel 用的）：精度高，内存换精度；
- **漏桶**：恒定速率出水，**削峰**但不允许突发；
- **令牌桶**：允许一定突发（桶容量），**大多数业务场景用这个**；
- 还有 **Redis + Lua 的分布式令牌桶**（原子扣减），以及 **Sentinel 的热点参数限流**。

**单机 vs 集群**：
- 单机限流：本地计数器，无网络开销，性能最好，但**机器数变化时限流总量漂移**，且负载不均时有的机器打满有的空闲；
- 集群限流：Redis 集中计数，总量精确，但每次请求一次 Redis（RT + 单点压力），且 Redis 故障时限流失效 → 一般做 **Redis 不可用降级为单机限流**；
- 折中：**单机限流为主 + 集群配额定期同步**（比如每秒从 Redis 拉一次本机的配额），兼顾性能与精度。

**在 AICC 里的应用点**：
- 放号速率限流（最核心）；
- ASR/TTS/LLM 调用按供应商配额限流；
- 开放 API 按租户限流（多租户隔离，防止一个客户打满）；
- **接线口限流要配合排队和降级**，而不是硬拒绝——呼叫类请求被拒的代价很高，优先排队 + 提示，而不是 503。

**我实际用过**：Sentinel（菜鸟技术栈），配置限流规则 + 熔断规则；diamond/switch 做开关，紧急情况一键降级。

### Q26. 熔断和降级的区别？怎么配置？

**回答：**

- **熔断（Circuit Breaker）**：针对**下游依赖**。下游错误率/慢调用比例超过阈值 → 直接**快速失败**，不再调用，保护自己也给下游喘息；过一段时间后进入**半开状态**放少量请求试探，成功则关闭熔断。典型：Sentinel 的 `慢调用比例` 和 `异常比例` 熔断，或 Resilience4j。
- **降级（Degradation）**：针对**自己**。系统压力过大或依赖不可用时，**牺牲非核心功能保证核心链路**，返回兜底结果。比如：AI 质检停掉但呼叫继续；画像拉取失败就用基本信息；推荐话术不可用就不弹。

**配置原则**（讲出具体经验值更有说服力）：
- 熔断阈值不能一刀切，按依赖的重要性分级：**强依赖**（支付、呼叫控制）阈值放宽 + 快速重试；**弱依赖**（画像、推荐）阈值收紧，早熔断早降级；
- 慢调用阈值要基于**依赖的 P99**，而不是平均值，否则正常波动就熔断了；
- 熔断后的**恢复要慢**（半开放少量流量逐步恢复），避免刚恢复就被打挂；
- 降级开关必须**可一键生效**（配置中心推送，秒级），且要有**降级演练**——我见过太多"开关写了但从没验证过，真出事时发现降级链路本身也是坏的"。

**我在 AIPhone 的实战**：LLM 是外部依赖，我给它配了超时 + 熔断 + 模板话术降级，并且用置信度前置过滤把调用量降下来，从源头减少对外部依赖的压力——**最好的容错是不依赖**。

### Q27. 削峰填谷怎么做？

**回答：**

三类手段：

1. **MQ 削峰**：突发写入先落 MQ，消费者按自己的处理能力匀速消费。典型场景：话单写入、录音转写任务、质检任务、批量任务导入。RocketMQ/Kafka 天然做这个。
2. **延迟/定时调度**：把非实时任务调度到低峰期。比如质检批处理、报表、数据归档、批量外呼任务放到夜间。
3. **批量合并**：把多次小请求合并成批量请求（写库 merge、批量调用 AI 接口、批量写 ClickHouse），大幅降低 IO 次数。ClickHouse 尤其要批量写入（单批 1w-10w 行）。

**配合机制**：
- **堆积监控 + 动态扩缩容**：MQ 堆积量是扩容信号，消费者按堆积量弹性扩容；
- **背压**：上游要能感知下游压力（比如 Netty 的 write buffer 水位、MQ 堆积阈值触发上游限流），否则只是把压力从服务转移到 MQ，最后 OOM；
- **优先级**：削峰时不能让重要消息排在后面，用**优先级队列**或**独立 topic**隔离核心链路和非核心链路（质检和大模型批处理绝不能挤占呼叫控制消息）。

### Q28. 缓存怎么治理？穿透、击穿、雪崩？

**回答：**

- **穿透**（查不存在的 key，绕过缓存打 DB）：**布隆过滤器**拦截 + **空值缓存**（短 TTL）。外呼场景典型：查一个不存在的号码归属、查黑名单。
- **击穿**（热点 key 过期瞬间大量请求打到 DB）：**互斥锁重建**（单飞，只有一个线程回源）或**逻辑过期**（物理不过期，异步刷新）。热点如：任务配置、活动配置、热词表。
- **雪崩**（大批 key 同时过期）：**TTL 加随机抖动** + 多级缓存（本地 Caffeine + 分布式 Redis）+ 缓存预热。
- **一致性**：**Cache Aside**（更新 DB 后删缓存）为主；高一致要求用**延迟双删**或**订阅 binlog（Canal）异步删缓存**；接受短暂不一致的场景用 TTL 兜底。**永远不要先删缓存再更新 DB**（会有脏数据回填）。
- **大 key / 热 key**：大 key 拆分（比如一个技能组的坐席列表拆成多个 key）、压缩、禁止一次性 hgetall；热 key 用**本地缓存 + 分片**（key 加随机后缀）打散到不同 Redis 节点。
- **可观测**：命中率、大 key 扫描、慢命令、内存水位、key 分布。我做过 SRE，习惯是**缓存必须配命中率告警**，命中率突降往往意味着代码 bug 或缓存被冲掉。

**AICC 场景**：线路配额、技能组配置、客户画像、话术模板、黑名单（布隆过滤器），这些是缓存的主战场；而**呼叫状态这类强一致强实时的数据不要缓存**，直接走 DB + 状态机，缓存反而会引入一致性风险。

### Q29. 讲讲你做过高并发系统的真实经历。

**回答（用开放平台，讲清楚"量、手段、结果、坑"）：**

在细叶科技我独立设计研发了**数趣云开放平台**，把对接银行和第三方支付的收款能力封装成二维码支付、JS Web 支付、扫码支付等标准产品对外提供，**日均交易流水 5000 万**。

**架构**：Spring Boot + Dubbo + Zookeeper 做服务化，MySQL 分库 + MyBatis，Redis 做配置和热点缓存，RabbitMQ 做异步解耦，Nginx/Tengine 做网关层和限流。

**关键手段**：
- **幂等**：所有支付和回调接口以**商户订单号 + 交易类型**做唯一键，DB 唯一索引兜底，Redis SETNX 前置去重，防止重复扣款；
- **异步解耦**：支付结果通知、对账文件生成、账务流水等非关键路径全部 MQ 异步化，主链路只做"扣款 + 记流水"；
- **限流与隔离**：按商户维度限流（防止一个大商户打满全站），核心接口和非核心接口线程池隔离；
- **对账与补偿**：每日与银行对账，差异走自动补偿 + 人工兜底，**支付系统里对账兜底比什么都重要**；
- **监控告警**：交易成功率、响应 RT、渠道错误码分布实时监控，渠道失败率超阈值自动切换备用渠道。

**踩过的坑**：
- 早期把回调通知和主流程放一个线程池，渠道回调慢把线程池打满，导致主流程不可用 → 后来做**线程池隔离**；
- 数据库热点商户的行锁竞争 → 按商户 ID 分片 + 异步合并入账。

**迁移到 AICC**：话单和计费就是支付交易的翻版——同样要求幂等、不丢单、可核对。而运营商渠道切换 = 支付渠道切换，失败率熔断 + 备用线路，逻辑完全一样。

### Q30. 异步化有哪些手段？什么时候不该异步？

**回答：**

**手段**：MQ 解耦、线程池/协程、事件驱动、批量合并、延迟任务、CDC（binlog 订阅）把业务和派生逻辑解耦、Reactive（WebFlux/Reactor）提升 IO 密集场景的吞吐。

**不该异步的情况**（这半段才是区分度）：
1. **要求强一致和即时反馈的**：扣款结果、呼叫发起的确认——用户/系统在等结果，异步只会增加复杂度且无法及时报错；
2. **异步后无法补偿的**：没有重试和幂等保障的链路不要异步，丢了就是丢了；
3. **本来就很快的同步调用**：硬做成异步，带来的复杂度（状态机、幂等、回调、对账）远超收益；
4. **异步链路上的超时和一致性成本高于同步时**：比如一个只需 5ms 的查询，异步化后要维护请求-响应关联、超时、乱序处理，得不偿失。

**我的判断原则**：**先问"这个动作的结果，谁在多长时间内需要看到"**。需要秒级内看到的做同步；允许分钟级甚至小时级的做异步，且必须配套**幂等 + 重试 + 死信 + 对账**四件套。异步的真正成本不在代码，在于**可靠性保障和可观测性**。

### Q31. 分库分表怎么设计？

**回答：**

**什么时候分**：单表数据量超过 2000w-5000w 且索引和 SQL 已优化到位；或写入 QPS 打满单库。先做**归档和索引优化**，能不拆就不拆——拆分带来的复杂度（分布式事务、跨库查询、扩容）非常大。

**怎么拆**：
- **Sharding Key 选择**（最关键）：必须是最常用的查询维度，且**分布均匀**。AICC 场景：话单按 `客户ID 或 callId` 拆（查询以客户维度为主），外呼任务按 `任务ID + 客户ID`。不要选会倾斜的 key（比如按"城市"拆，一线城市会撑爆）。
- **拆分方式**：水平拆（按 key 哈希或范围）。哈希分布均匀但范围查询要扫多库；范围（按时间）适合**冷热分离**（历史话单按月归档），这是外呼/话单这种时序数据的首选——**按时间做冷热分离 + 热库内按客户哈希**。
- **全局 ID**：用 Sequence 服务/雪花算法，避免自增主键冲突。我在菜鸟用的是 TDDL + 分布式 Sequence。
- **跨库查询**：避免 join，走**应用层聚合**或**异构索引**（冗余一份按另一个维度分片的数据，或同步到 ES/ClickHouse 做查询）。
- **扩容**：尽量**翻倍扩容**（2→4→8，减少数据迁移），或用一致性哈希；必须有**双写 + 校验 + 切流**的平滑迁移方案，绝不停机硬切。
- **热点**：某个 key 特别热（比如大客户的任务）→ 加随机后缀打散，读取时聚合。

**AICC 落地**：话单表是典型的大表（千万级/天），我的方案是**按月分库分表 + 热数据(近 3 个月)在 MySQL、冷数据归档到 Lindorm/HBase 或对象存储，分析查询走 ClickHouse/ES**。这也顺便对上了岗位要求的 ClickHouse。

> **加分点**：提一句"**TDDL 我在菜鸟实际用过**"，比空谈理论强得多。

## 6. 微服务治理（岗位第 5 条）

### Q32. 服务怎么拆分？拆分的粒度怎么把握？

**回答：**

**原则**：
1. **按业务能力 / 领域边界拆**，不按技术分层拆（不要搞出"一个 service 层一个服务"）；
2. **单一职责 + 高内聚低耦合**：一个服务拥有一份数据，其他服务通过接口访问，不直接跨库；
3. **康威定律**：服务边界尽量匹配团队边界，一个服务有明确的 owner；
4. **演进式拆分**：**先拆"变化频率不同"和"伸缩需求不同"的模块**，不要一开始就追求完美的领域模型。

**粒度的判断标准**（实用的四条）：
- **拆太粗**：任何改动都要全量发布、互相影响、无法独立扩容；
- **拆太细**：分布式事务泛滥、调用链过长（RT 累加、可用性是各服务相乘）、排查困难、运维成本高；
- **我的经验值**：一个服务由 **1-2 个团队（3-8 人）维护**比较合适；调用链深度控制在 **3-4 层**以内；**如果拆开后需要分布式事务保证强一致，说明拆错了**，应该合并或改成最终一致。

**AICC 拆分示例**（展示你能把原则落到这个业务上）：
- `呼叫控制服务`（SIP/CTI 适配、呼叫状态机）—— 长连接、有状态、高实时性，**独立部署独立扩容**；
- `外呼任务调度服务`（任务/批次/放号/重拨）—— 计算密集、批量，**可独立伸缩和错峰**；
- `AI 编排服务`（ASR/TTS/LLM/RAG 编排）—— 外部依赖多、成本和延迟敏感，**独立限流降级**；
- `坐席服务`（坐席状态、技能组、排班）—— 状态频繁变更；
- `客户/名单服务`（客户画像、号码名单、DNC 黑名单）；
- `话单与计费服务`（CDR、计费、对账）—— 写多读少、大数据量，**独立分库分表**；
- `质检与会话分析服务` —— **离线/准实时批处理，与实时链路物理隔离，绝不能互相影响**。

拆分的理由要讲清楚：**变化频率不同 + 资源特征不同 + 可用性等级不同**。

### Q33. 服务注册发现、配置中心、链路追踪怎么做的？

**回答：**

- **注册发现**：Dubbo + Zookeeper（我实际用过），或 Nacos/Eureka。要点：**健康检查要真实**（不是只检查进程活着，要检查依赖和关键资源）；**服务上下线要有优雅停机**（先摘流量，再等处理中的请求完成）；**推拉的平衡**（大规模下用推送 + 本地缓存，避免注册中心抖动引发雪崩）；注册中心本身要**集群化且不能是强依赖**（本地有缓存文件兜底）。
- **配置中心**：我在菜鸟用 diamond + switch，等价于 Nacos/Apollo。要点：**配置变更要可灰度、可回滚、有审计**；**开关类配置和业务配置分开**（开关要秒级生效，业务配置可以有版本）；配置的**默认值和防错校验**很重要（一个错的配置推送下去就是全站故障）；敏感配置加密。
- **链路追踪**：SkyWalking（无侵入字节码增强）或 Jaeger（OpenTelemetry 标准）。要点：**TraceId 要贯穿全链路**，包括 MQ 消息（消息带上 traceId，消费端续上）和异步线程（线程池要传递上下文，这是最常见的断链点）；**采样策略**（低采样省成本，但错误请求要全采）；**trace 要和日志、指标打通**（从 trace 跳到日志，从指标下钻到 trace）。
- **在语音场景的特殊点**：一通电话是**跨多个服务的长事务**，trace 的粒度要按 callId 聚合，所以我一定会把 **callId 作为 trace 的 business tag**，这样才能一次看完整通电话的全链路——这是我做过的"按会话维度聚合日志做质量分析"的同类思路。

### Q34. 灰度发布怎么做？

**回答：**

**维度**：按机器（beta 节点）、按流量比例、按用户/租户/号码批次（最常用也最安全）、按地域。

**完整流程**（"发布不是最后一公里，是全流程"）：
1. **代码层面**：新功能走**开关（feature flag）**，代码先上线但功能关闭，发布与生效解耦；
2. **流量层面**：网关/Dubbo 的 tag 路由，把带灰度标的用户路由到灰度实例；
3. **数据层面**（最容易踩坑）：**灰度期间的数据结构必须向后兼容**（只加字段不改语义），否则回滚时老代码读不了新数据；数据库变更要**先加字段 → 双写 → 校验 → 切读 → 停双写 → 删旧字段**的渐进式流程；
4. **观察**：灰度期间盯**错误率、RT、业务指标**（比如 AI 外呼的意图准确率、接通率），而不只是技术指标；
5. **回滚**：一键切流回滚 + 开关关闭，**回滚方案要在发布前就验证过**。

**AICC 的灰度特别重要**：因为外呼是**直接触达真实用户**的，一次话术 bug 可能是几万通错误电话和大量投诉。所以我的做法是：**新话术/新模型先在 1% 的小流量上跑，人工抽检录音，确认无问题再逐步放大到 10% → 50% → 100%**，并保留随时一键回退到上一版话术的能力。

### Q35. 容量评估和压测怎么做的？

**回答：**

**容量评估三步**：
1. **建模**：把业务目标翻译成技术指标。比如"日外呼 1000 万通" → 峰值 CPS、并发通话数、AI 服务 QPS 和并发连接、写库 QPS、MQ 吞吐。
2. **单机基线**：压测出单机的**容量水位**（CPU/内存/连接数/RT 的拐点），不能只看"能跑多少 QPS"，要看**RT 恶化到 SLO 边界时的 QPS**。
3. **推算与冗余**：`机器数 = 峰值负载 / 单机安全水位`，再乘冗余系数（一般按峰值的 1.5-2 倍容量预留），并且**关键服务要能扛住单点故障**（N+1）。

**压测要点**：
- **全链路压测**（不是单接口）：流量要**模拟真实波形和真实数据分布**（外呼是批量突发的，号码分布、话术分布也要真实）；
- **隔离**：压测流量要打标（影子表、影子队列、压测账号），绝不能污染生产数据和真实用户——尤其是外呼，**压测绝不能真的拨出电话**（要用模拟网关/空号段）；
- **逐级加压 + 破坏性测试**：找到系统的**拐点和崩溃点**，验证限流熔断降级是否真的生效；
- **常态化**：容量会随代码迭代漂移，所以要**定期压测**，或做常态化压测（低峰期在隔离环境跑）。

**我做过的事**：在菜鸟做 SRE 时我关注的是**水位和告警有效性**——压测之外更重要的是**平时的水位监控和预警**，在到达容量红线之前就扩容，而不是等故障。

### Q36. 故障隔离怎么做？

**回答：**

- **物理隔离**：核心链路（呼叫控制）和非核心链路（质检、报表、挖掘）**独立部署、独立资源池、独立 MQ topic**，互不抢占；
- **线程池/信号量隔离**：不同依赖用不同线程池（Hystrix/Sentinel 的思路），防止一个慢依赖耗尽线程；
- **多租户隔离**：按租户/客户做**配额和限流**，防止一个大客户拖垮全站（我在支付开放平台就按商户限流）；
- **数据隔离**：核心库和非核心库分开，分析型查询走只读库/ClickHouse，不在主库跑大查询；
- **依赖降级与熔断**：弱依赖全部可降级；
- **部署隔离**：按可用区/机房部署，避免单机房故障；
- **故障域控制**：灰度、分批发布、配置分批推送，**任何变更都不能一次性作用于全量**；
- **超时必须设置**：所有跨服务调用**必须有超时**，这是最便宜也最常被忽略的隔离手段——没有超时的系统，一个慢依赖就能拖垮整条链路。

## 7. 存储与消息中间件（岗位第 6、7 条）

### Q37. MySQL 索引优化和慢 SQL 怎么排查？

**回答：**

**排查流程**：
1. 开启**慢查询日志** + 用 `EXPLAIN` 看执行计划：重点看 `type`（至少到 range，最好 ref/const，避免 ALL）、`key`（是否走了预期索引）、`rows`（扫描行数）、`Extra`（`Using filesort` / `Using temporary` 是危险信号）；
2. 看**是否命中联合索引的最左前缀**，以及**索引区分度**（重复值多的列放后面，或者干脆不适合单独建索引）；
3. 检查**隐式类型转换**（varchar 字段传了数字 → 索引失效）、**函数/表达式包裹列**（`DATE(create_time)=...` 失效）、`like '%xx'` 前缀通配失效、`or` 导致索引失效；
4. 分页深翻（`limit 1000000, 20`）→ 用**游标分页**（where id > last_id）；
5. 大表 DDL 用 `pt-online-schema-change` / `gh-ost` 在线改表，不要直接 alter。

**优化手段**：覆盖索引避免回表、联合索引顺序（等值列在前、排序列在后）、适当冗余字段减少 join、**冷热分离归档**、读写分离、必要时上 ES/ClickHouse 做检索和分析。

**AICC 场景的典型慢 SQL**：话单表按时间范围 + 客户 ID 查询 → 联合索引 `(customer_id, start_time)`；质检结果的多维度聚合 → 不要在主库做，同步到 ClickHouse 做。

> **加分点**：说一个真实案例效果最好。准备一个"我把某个 SQL 从 X 秒优化到 Y 毫秒"的故事（哪怕是小 SQL），比背八股文有用得多。

### Q38. Redis 和 MySQL 一致性怎么保证？

**回答：**

先说结论：**强一致做不到也不该做，我们追求的是"最终一致 + 可接受的时间窗口"**。

**常用方案**：
1. **Cache Aside（推荐）**：读 → 缓存没有则读 DB 回写缓存；写 → **先更新 DB，再删除缓存**（不是更新缓存，避免并发写导致脏数据和无效计算）。
2. **延迟双删**：删缓存 → 更新 DB → sleep 一小段时间 → 再删一次。解决"读请求在更新 DB 期间把旧值回填进缓存"的问题。
3. **binlog 订阅（Canal / DTS）**：更新 DB 后，由中间件订阅 binlog 异步删除缓存，**业务代码零侵入**，且能保证不漏（MQ 保障可靠）。这是大厂主流做法，我在菜鸟见过类似的架构。
4. **兜底**：所有缓存设 TTL，即使删除失败，TTL 到了也会自愈。**TTL 是最后一道防线，不要设永不过期**。

**特殊处理**：
- 热点 key 的重建要做**单飞**，避免缓存失效瞬间几千个请求同时回源打爆 DB；
- 双写期间要**校验**（定期对账缓存和 DB），我在支付系统里养成的习惯是**任何异步链路都要有对账**。

### Q39. MQ 怎么保证消息不丢、不重复、有序？

**回答（RocketMQ/MetaQ 为主，我实际用过）：**

**不丢**（三处都要保证）：
1. **生产端**：同步发送 + 失败重试；关键消息用**事务消息**（half message → 本地事务 → commit/rollback，MQ 回查本地事务状态）；
2. **Broker**：**同步刷盘 + 主从同步复制**（sync_flush + sync_master），代价是性能，所以只对关键链路开；
3. **消费端**：**业务处理成功后才 ACK**，失败则重试；重试多次进**死信队列**，人工/自动补偿，绝不静默丢弃。

**不重复（幂等）**：MQ 只保证**至少一次**，重复无法避免，所以**幂等必须在消费端做**：
- 唯一键去重表（DB 唯一索引，插入成功才处理）；
- Redis SETNX（带 TTL）；
- 状态机幂等（"已完成的订单再收到完成消息直接忽略"）；
- 我在支付平台就是靠"商户订单号 + 类型"的唯一索引 + 状态机保证的。

**有序**：
- **全局有序**代价太大，实际用的是**局部有序**：同一业务 key（如 callId、订单号）的消息发到同一个 queue/partition，且**单线程消费**该 queue；
- 消费失败时**不能跳过**（跳过就乱序了），要重试当前消息（RocketMQ 的顺序消息会暂停该队列）→ 所以顺序消息的消费逻辑必须**可重试且幂等**；
- 更稳的做法：**消息带版本号/序号，消费端做乱序检测和重排**，不依赖 MQ 的严格顺序。

**堆积处理**：先看是**生产突增**还是**消费变慢**（消费变慢通常是下游 DB/接口慢或异常重试）。应急：扩容消费者（注意分区数限制）、临时 topic 分流（把堆积消息转到一个多分区的临时 topic，起大量消费者快速消化）、降级非核心消费。

### Q40. 事务消息怎么用？延迟消息呢？

**回答：**

**事务消息**（RocketMQ 的 Half Message 机制）：解决"本地事务和消息发送的原子性"。
1. 发送 half message（对消费者不可见）；
2. 执行本地事务（比如插入话单）；
3. 根据结果 commit（消息可见）或 rollback（消息丢弃）；
4. 如果第 3 步没执行（服务挂了），Broker 会**回查**本地事务状态，所以**必须实现事务回查接口**，且回查要幂等。

**使用场景**：外呼任务创建后要确保"任务落库 + 调度消息一定会发"，用事务消息比"先入库再发消息"更可靠。

**替代方案**（我更常用的）：**本地消息表 + 定时任务补偿**——本地事务里同时写业务表和消息表（同一个 DB 事务保证原子），再由独立任务扫描消息表发送，失败重试直到成功。好处是简单、可观测（消息就在库里，好查好补），缺点是有一点点延迟和 DB 压力。还有更轻量的 **CDC（订阅 binlog）**方案。

**延迟消息**：RocketMQ 支持固定延迟级别（1s/5s/10s/30s/1m/...），不够灵活时自己实现**时间轮（TimingWheel）**或用 Redis ZSet 做延迟队列，或 DB + 定时扫描（简单可靠）。
**AICC 场景**：**未接通自动重拨**（延迟 5 分钟再呼）、**预约回呼**（客户指定的时间）、**话后处理超时自动释放坐席**、**30 分钟后触发质检任务**——延迟消息是外呼系统的基础设施。

### Q41. ClickHouse / ES / MongoDB 在 AICC 里怎么用？

**回答（ClickHouse 简历没写，要用"迁移能力"话术补）：**

- **ClickHouse**：**列式存储，适合大规模 OLAP 聚合分析**。AICC 里用于话单/呼叫记录的多维分析（按时间、线路、地区、坐席、意向等级聚合）、接通率趋势、成本分析、质检结果统计。要点：**批量写入**（单批 1w+ 行，低频次）、按时间分区、**避免高频单行更新**（它是追加写友好的，更新是异步 mutation）、**JOIN 要小心**（大表 join 内存爆炸，尽量宽表预聚合）。我没有生产用过 ClickHouse，但我用过 Lindorm 和 Tablestore 这类列式/宽表存储，也做过 ES 的聚合分析，列存的建模思路（宽表 + 预聚合 + 分区）是相通的，上手不难。
- **Elasticsearch**：**检索**。通话转写文本全文检索（找"某客户说过投诉"）、知识库检索、日志检索。要点：合理的 mapping 和分词（中文用 IK）、避免深分页（用 search_after）、写多读多的场景要控好分片数。
- **MongoDB**：**半结构化数据**。对话上下文、动态话术模板、配置类 JSON 数据。我用 MongoDB 做过实际项目（早期 Python + Pyramid + MongoDB）。
- **Redis**：呼叫状态、坐席席位锁、配额计数、限流、分布式锁、延迟队列。

**选型原则（体现判断力）**：**写入密集且要分析的用 ClickHouse；要全文检索的用 ES；强一致事务的用 MySQL；半结构化且 schema 易变的用 MongoDB；低延迟状态用 Redis。一个系统用多种存储是正常的，但要控制运维成本——能少一种就少一种。**

### Q42. Redis 分布式锁怎么实现？有什么坑？

**回答：**

**实现**：`SET lock_key requestId NX PX expireTime`（加锁原子）+ Lua 脚本校验 requestId 再删锁（解锁原子，防止误删别人的锁）。Java 用 Redisson 的 `RLock`（自带 watchdog 自动续期）。

**坑**：
1. **业务没执行完锁过期了** → 需要**自动续期**（Redisson watchdog）或把过期时间设得足够大 + 业务侧兜底校验；
2. **误删别人的锁** → 解锁必须校验 value（requestId）；
3. **主从切换导致锁失效**（主节点写入未同步就挂了，从节点被选为主，锁丢失）→ Redlock 有争议，实践中更常用**业务层幂等 + 状态机**做最终兜底，而不是依赖锁的绝对可靠；
4. **不可重入** → 用可重入锁（Redisson 支持）；
5. **锁粒度太粗影响并发，太细增加复杂度**；
6. **GC STW / 线程停顿导致锁超时** → 监控 JVM 停顿。

**我的观点**：**分布式锁是"尽力而为"的优化手段，不是正确性保障**。正确性必须由**DB 唯一索引 + 状态机 + 幂等**保证。比如在扣减外呼配额时，锁可以做前置快速失败，但真正的扣减要用**原子操作（Redis Lua 或 DB 条件更新 `where quota >= 1`）**保证不超发。这个观点我在支付系统是必须坚持的——钱的事不能靠锁。

### Q43. 数据库死锁和行锁等待怎么处理？

**回答：**

**排查**：`show engine innodb status` 看最近死锁日志（哪两个事务、哪些 SQL、持有的锁和等待的锁）；或用 `information_schema.innodb_trx` / `performance_schema` 查当前长事务和锁等待。

**常见原因与解法**：
- **更新顺序不一致**（事务 A 先更新行 1 再行 2，事务 B 相反）→ **统一更新顺序**；
- **热点行并发更新**（比如同一个任务的计数器）→ **拆行**（多行求和）或**异步合并**（先写明细，异步汇总）；
- **大事务**（一个事务更新几万行、持锁时间长）→ **拆小事务**，事务里不要有 RPC 和慢 IO；
- **索引缺失导致锁范围扩大**（RR 隔离级别下，没索引的 update 会锁大量记录甚至全表）→ **加索引**；
- **间隙锁**（RR 下的 next-key lock）→ 业务允许的话改 RC + row 格式 binlog，或调整查询条件避免间隙锁。

**预防**：设置 `innodb_lock_wait_timeout`（默认 50s 太长，一般设 5-10s）+ **锁等待监控告警** + 代码规范（事务尽量小、顺序一致、避免事务内 RPC）。

**AICC 场景**：批量外呼任务的计数器、坐席状态更新、配额扣减都是热点行——我的做法是用**原子条件更新 + 明细异步汇总**，避免在同一行上长时间持锁。

## 8. Java / Netty / 性能（岗位第 3、8 条）

### Q44. Netty 的线程模型？为什么性能高？

**回答：**

**线程模型（Reactor 主从多线程）**：
- **BossGroup**（一般 1 个线程）：只负责 `accept` 新连接，然后把连接注册到 WorkerGroup；
- **WorkerGroup**（默认 CPU 核数 × 2 个线程）：每个 `NioEventLoop` 绑定一个 Selector，负责多个 Channel 的读写和事件处理；**一个 Channel 只绑定一个 EventLoop，整个生命周期不变**，所以同一个连接的处理是**单线程的**，无需加锁；
- **业务处理**要丢到独立的业务线程池，避免阻塞 EventLoop（**绝不能在 handler 里做慢 IO**）。

**高性能的原因**：
1. **NIO 多路复用**：一个线程管理成千上万连接，避免"一连接一线程"的上下文切换和内存开销；
2. **零拷贝**：`ByteBuf` 的堆外直接内存（DirectBuffer）减少一次内核态到用户态拷贝；`CompositeByteBuf` 避免合并拷贝；`FileRegion` 用 `sendfile` 做文件传输零拷贝；
3. **内存池化**：`PooledByteBufAllocator` 复用内存，减少 GC 和分配开销；
4. **无锁串行化**：一个 Channel 一个 EventLoop，避免锁竞争；
5. **Pipeline 责任链**：handler 可插拔，编解码/心跳/业务逻辑解耦；
6. **引用计数**：ByteBuf 用完必须 `release()`，否则**堆外内存泄漏**（Netty 有 leak detector，但要靠 `-Dio.netty.leakDetection.level=advanced` 和监控发现）。

**工程要点**：心跳（`IdleStateHandler`）、粘包拆包（`LengthFieldBasedFrameDecoder`）、背压（写缓冲区水位 `WRITE_BUFFER_WATER_MARK`，`channel.isWritable()` 判断后暂停生产）、优雅停机。

**在 AICC 的应用**：坐席工作台的**长连接信令推送**（WebSocket）、与 FreeSWITCH ESL 的长连接、海量呼叫事件的上报。十万级并发连接靠的就是这套模型。

> **加分点**：提"我用 WebFlux/Reactor 做过 Reactive 开发"，说明你对异步非阻塞不只是会用 Netty，还理解响应式编程模型。同时提一个坑：**Reactor/异步代码的栈信息丢失，排查困难，所以必须靠 traceId 和结构化日志**。

### Q45. 讲讲 JVM 调优和线上问题排查。

**回答：**

**排查 CPU 高**：
1. `top` 找进程 → `top -Hp` 找线程 → `jstack` 取线程栈，把线程 ID 转十六进制对应 nid；
2. 常见原因：**死循环/正则回溯、频繁 GC、大量线程上下文切换、锁竞争**；
3. 若 GC 线程占高 → 看内存问题。

**排查内存 / OOM**：
1. `jmap -dump` 导出堆（注意会 STW，生产要谨慎）+ MAT 分析 dominator tree 找大对象和 GC root；
2. 先看 `jstat -gcutil` 看各区使用率和 GC 次数，判断是**内存泄漏**（老年代持续上涨、FGC 后不降）还是**内存配置不足**；
3. 堆外内存泄漏：Netty DirectBuffer 未释放、`ByteBuffer.allocateDirect`、JNI、压缩类（`META-INF` 解压用堆外）——`NMT`（Native Memory Tracking）可以跟踪。

**GC 调优（原则优先于参数）**：
- 先确认是不是**代码问题**（对象生命周期过长、大对象、缓存无上限、线程数过多），调优前先做**对象分配优化**，GC 调参是最后手段；
- 参数：选 G1（大堆、低延迟）或 ZGC（超大堆、极低延迟）；设 `-Xms = -Xmx` 避免动态扩缩；设 `MaxGCPauseMillis` 目标；开 GC 日志和 OOM 时自动 dump（`-XX:+HeapDumpOnOutOfMemoryError`）；
- 用 Arthas 在线诊断（`dashboard`/`thread`/`watch`/`trace`/`heapdump`），这个我在细叶科技就用过。

**我的方法论**：**先保护现场（摘流量/保留一台实例不重启），再取证据（线程栈/堆/GC 日志/监控曲线），再定位，最后复盘**。我做过 SRE，知道"先恢复再定位"的边界——**故障处理第一优先级是恢复业务**（回滚/切流/扩容/降级），而不是在现场死磕根因。

### Q46. ConcurrentHashMap、线程池、锁，你踩过什么坑？

**回答：**

- **ConcurrentHashMap**：`size()` 在并发下不精确（用 `mappingCount`）；`computeIfAbsent` 内不能再修改同一个 map（可能死锁）；**复合操作不保证原子**（check-then-act 要额外加锁）。
- **线程池**（最常踩）：
  - **用 `Executors` 的默认工厂会踩坑**：`newFixedThreadPool` 的队列是**无界 LinkedBlockingQueue**，OOM；`newCachedThreadPool` 最大线程数无界，OOM。必须**手动 `new ThreadPoolExecutor`**，明确队列大小、拒绝策略和线程名（**线程名一定要自定义，排查时救命**）；
  - **核心/最大线程数设置**：CPU 密集 ≈ N 核；IO 密集要按 **等待时间/计算时间** 的比值放大，而不是拍脑袋；
  - **拒绝策略**：重要任务用 `CallerRuns`（让调用方慢下来，天然背压）或自定义"落库 + 补偿"，不要用 `AbortPolicy` 静默丢弃；
  - **父子线程上下文丢失**（traceId、MDC、ThreadLocal）→ 用 `TransmittableThreadLocal` 或装饰器传递；
  - **异常处理**：`submit` 的异常会被吞进 Future，必须用 `execute` 或捕获 Future 异常。
- **锁**：`synchronized` 不能跨 JVM；`ReentrantLock` 必须 finally unlock；**锁的粒度**要在"正确性"和"并发度"之间权衡；能用无锁（CAS/原子类/LongAdder）就不用锁；**LongAdder 在高并发计数场景远优于 AtomicLong**（分段）。

### Q47. 你主导的注解驱动 RPC 框架是怎么回事？（**必问，因为是简历亮点**）

**回答：**

在细叶科技我们大量用 Dubbo，但 Dubbo 原生的服务暴露和引用需要写 XML 或大量 `@Service`/`@Reference` 配置，且团队里配置项容易写错、重复代码多。

我做的 `rpc-dubbo-spring-boot-starter` 做的事情：
1. 提供 **`@RpcProvider`**（标注在实现类上，自动暴露为 Dubbo 服务）和 **`@RpcConsumer`**（标注在字段上，自动注入远端服务引用）两个注解；
2. 底层用 **Spring 的 `BeanPostProcessor` / `BeanFactoryPostProcessor` + `ImportBeanDefinitionRegistrar`** 在 Spring 容器启动时扫描注解，动态注册 BeanDefinition；
3. 服务引用用 **JDK 动态代理**（Dubbo 本身也是），在注入时生成代理对象，调用时走 Dubbo 的 Invoker 链路；
4. 统一收敛了超时、重试、序列化、分组、版本等配置到 starter 的默认配置 + 配置中心，避免每个人自己配错；
5. 兼容 Spring Boot 的自动装配（`spring.factories` / `AutoConfiguration`），做到**引入 jar 即用**。

**效果**：开发效率提升约 40%（主要来自配置收敛和消除样板代码），同时因为配置统一，**线上因为超时/重试配置不当导致的问题明显减少**。

**收获**：做这个东西让我真正理解了 **Spring 的扩展点体系**（BeanPostProcessor、BeanFactoryPostProcessor、ImportSelector、自动装配）和**动态代理在 RPC 中的应用**，也让我之后看任何框架的 starter 都能很快看懂它的原理。

> **追问准备**：
> - "和 `@DubboService/@DubboReference` 有什么区别？" → 那个年代 Dubbo 的注解能力还不完善（2.6），我们做的是**团队规范收敛层**：不只是简化，更重要的是**强制统一配置项**（超时、重试、注册中心分组），这是治理价值。
> - "动态代理用 JDK 还是 CGLib？" → JDK 动态代理（基于接口，Dubbo 是接口级代理）；CGLib 基于继承，不能代理 final 类/方法。
> - "怎么解决循环依赖/启动顺序？" → 服务引用用懒加载代理（注入的是代理对象，真正调用时才初始化），避免启动期的依赖顺序问题。

### Q48. 怎么保证代码质量和架构不腐化？

**回答：**

**机制层面（靠制度而不是靠自觉）**：
1. **代码评审**：PR 必须评审，我 review 时重点看**接口设计、异常处理、幂等与并发、日志与监控、是否引入新依赖**，而不是盯代码风格（风格交给工具）；
2. **静态检查**：Checkstyle/SpotBugs/SonarQube 接入 CI，**卡住明显问题**，代码风格用工具自动格式化（Prettier/spotless），不在 review 里争论；
3. **分层与依赖约束**：定义清楚分层（controller/service/domain/infra），禁止跨层调用，用 ArchUnit 做**架构约束的自动化校验**（这个很加分）；
4. **接口规范**：统一的响应结构、错误码、幂等约定、分页约定、超时约定；接口变更必须**向后兼容**；
5. **技术债管理**：每次迭代留固定比例的时间还债，技术债要有**清单和优先级**，不能只口头说；
6. **复盘机制**：每次故障复盘产出 action item 并跟踪闭环，我做过 SRE，最怕的是"复盘写了，改进项没人跟"。

**文化层面**：owner 意识（谁写的代码谁负责线上）、鼓励说出问题而不是掩盖、把"稳定运行"作为评价的一部分而不只是"需求交付快"。

## 9. 稳定性与故障处理（岗位第 10 条，你有 SRE 实战）

### Q49. 讲一次你处理过的线上故障。

**回答（STAR 结构，务必准备一个真实故事）：**

**背景**：在 AIPhone，用户反馈面对面翻译会**突然冒出一串重复文本**，或者**文本一直在变**（流式幻听）。

**定位**：我没有直接改代码，而是先做数据分析——把 ASR 回调时间、句子时长、音频能量做关联，量化出每天有多少句受影响（重复 500+ 次/天，幻听流式 1000+ 次/天），确认这不是偶发而是**架构性问题**：模型侧 `Recognized` 事件会超时回调甚至不回调，而业务侧只靠超时阈值兜底，阈值调大延迟高、调小误截断，两难。

**方案与推动**：我提出把**超时断句的判定上移到模型侧**（模型根据自己的状态主动断句），业务侧**保留决策权**并保留超时兜底，形成双层架构。这个改动跨业务和模型两个团队，我组织了原方案设计者、组长、模型侧和 CTO 的技术评审，用数据讲清影响面、给出两种方案对比和灰度计划。

**结果**：上线后重复透出减少 500+ 次/天，幻听流式文本减少 1000+ 次/天。

**复盘沉淀**：（1）**异步事件链路不能只靠单一事件源，必须有超时兜底 + 主动对账**；（2）**判定权要放在离信息最近的地方**（模型侧更懂音频），**决策权放在离业务最近的地方**（业务侧更懂策略），这个分层原则我后来一直用。

> 备选故事（用于不同面试官偏好）：菜鸟 SRE 的告警治理——"告警噪音率 35%→15%，风险预警单日均 3.5→2"，讲清楚**怎么做的**（告警分级、无效告警清理、阈值调优、聚合收敛、明确 action）和**为什么重要**（告警疲劳会导致真故障被忽略，这是所有稳定性事故里最隐蔽的杀手）。

### Q50. 告警怎么治理？告警噪音怎么降？

**回答（你的真实成绩，要讲方法论）：**

**问题**：告警太多等于没有告警。噪音率 35% 意味着值班同学三分之一的精力在处理无效告警，长期会导致**告警疲劳**，真出故障时反应变慢甚至忽略。

**我做的事**：
1. **分类与分级**：把告警按**影响面**分级——P0（业务不可用，电话叫醒）/P1（核心指标异常，立即处理）/P2（需要关注，工作时间处理）/P3（提示）。**只有 P0/P1 才允许叫醒人**；
2. **清理无效告警**：逐条审视存量告警，问三个问题——"这条告警触发后我要做什么？"**没有明确 action 的告警直接删或降级为看板指标**；"阈值是不是拍脑袋定的？"用历史分布重新校准；"是不是重复告警？"合并同源告警；
3. **收敛与聚合**：同一根因的多个告警**聚合成一条**（比如依赖抖动导致 10 个接口告警，只报一条"依赖 X 异常"）；**告警风暴抑制**（瞬时大量同类告警合并为一条）；
4. **从"资源告警"转向"业务告警"**：CPU 高不一定有问题，**业务指标**（接通率、任务成功率、AI 响应延迟）才是真的用户影响；资源指标作为辅助定位；
5. **每条告警必须带 runbook**（处理步骤、负责人、止损手段），否则接告警的人不知道怎么办；
6. **闭环度量**：每月统计告警量、噪音率、响应时间，持续迭代。

**结果**：告警噪音率 35% → 15%，风险预警单从日均 3.5 降到 2。

**关键认知**：告警治理的目标不是"告警少"，而是**"每一条告警都值得被人叫醒"**。

### Q51. 故障复盘怎么做？

**回答：**

**原则**：**对事不对人（blameless）**，目的是防止再犯，不是追责。追责文化会导致隐瞒问题，那才是最危险的。

**流程**：
1. **时间线还原**：什么时候发生、谁发现的、怎么发现的（监控还是用户反馈——**用户先发现就是监控缺失，这本身就是一个改进项**）、什么时候止损、什么时候恢复；
2. **影响面量化**：影响多少用户/多少通电话/多少金额、持续多久、有没有合规风险；
3. **根因分析**：用 **5 Why** 挖到根因，区分**直接原因**（某行代码 bug）、**根本原因**（为什么没测试出来、为什么没监控到、为什么没有降级）、**系统性原因**（流程或架构缺陷）；
4. **改进项**：分三类——**止损手段**（能不能更快恢复）、**预防措施**（能不能不发生）、**发现手段**（能不能更早发现）。改进项必须**有 owner、有 deadline、可验收**，并跟踪闭环；
5. **复盘文档归档 + 分享**，让其他团队也受益。

**我特别看重的两条**：
- **"为什么没有更早发现"** —— 大多数故障的真实损失在于发现太晚，所以复盘一定要审视监控覆盖；
- **"止损手段是否有效"** —— 如果只能靠回滚代码恢复，说明**降级和容灾能力不足**，这比 bug 本身更值得改进。

### Q52. 微服务调用链很长，一个请求慢了怎么定位？

**回答：**

1. **先定位是哪一段慢**：用**链路追踪**（trace）看各 span 耗时，P99 而不是平均值；同时看是**全链路慢**（网络/网关/序列化）还是**某个服务慢**；
2. **看服务的四黄金指标**（延迟、流量、错误、饱和度）：如果只有错误率升高，是依赖问题；如果饱和度（CPU/线程/连接池）打满，是容量或阻塞问题；
3. **分层排除**：客户端 → 网关 → 应用 → 依赖（DB/Redis/MQ/下游）。每层看：RT、QPS、错误率、资源水位；
4. **常见根因清单**（快速对照）：DB 慢查询/锁等待、连接池耗尽、线程池打满、GC 停顿、网络抖动/DNS、依赖限流或熔断、热点数据、大对象序列化、日志同步刷盘阻塞；
5. **工具**：Arthas（`trace` 看方法耗时、`watch` 看入参返回值、`thread` 看阻塞）、`jstack`（线程栈）、`jstat`（GC）、`perf`（CPU 火焰图）、慢查询日志。

**语音场景的特殊点**：呼叫链路是**长连接 + 异步事件**，一次"慢"可能是**事件堆积**而不是接口慢，所以要监控 MQ 的**堆积量和消费延迟**，以及**从事件发生到被处理的端到端延迟**（我在做质量分析平台时就是这个思路：把全链路每个环节的时间戳打点，端到端度量）。

## 10. 团队管理（岗位第 8、12 条）

### Q53. 你怎么带团队？带过多少人？

**回答：**

我在细叶科技带过 **10 人团队**（研发 TL），在菜鸟长期作为项目 PM 带跨职能项目组（前后端 + 测试 + 产品 + 上下游域）。

**我的做法**：
1. **目标对齐**：每个迭代开始前，让每个人清楚**做什么、为什么做、做到什么程度算好**。我最怕的是同学只知道做需求不知道业务目标——那样遇到权衡时他无法自己做决策；
2. **拆解与节奏**：需求拆到**可独立完成、可验证**的粒度（一般 1-3 天一个任务），设置明确的里程碑和联调时间点，**风险前置**（依赖越多的任务越早排）；
3. **过程把控**：每日站会只讲三件事（昨天做了什么、今天做什么、有什么阻塞）；**阻塞超过一天的我亲自介入**；
4. **质量把关**：代码评审 + 接口评审 + 发布计划评审。我 review 的重点是**设计和风险**，不是风格；
5. **人才培养**：按能力分层授权——新人给明确的小任务和详细设计，熟手给模块和自主权；**让每个人有一块自己"_owner"的东西**，这是责任感最好的来源；
6. **跨部门协作**：我做 PM 的经验是**提前识别依赖并书面确认**（接口协议、时间点、责任人），出了问题先解决再复盘，不要在会上追责；
7. **1v1**：定期聊聊同学的困惑和成长诉求，不只聊工作进度。

**结果**：多个关键项目按期交付，猫超 88VIP 项目获集团红草莓奖，特惠当日取项目单量增长 761%。

### Q54. 团队成员能力不足/交付延期怎么办？

**回答：**

**先分类，再对症**：
- **能力问题** → 判断是"不会"还是"不知道要求"。不会就给**设计示范 + 结对**；不知道要求就明确验收标准。**能力问题本质上大多是管理问题**（任务给得太大、要求说得不清楚）；
- **态度问题** → 直接 1v1 谈，明确期望和后果，不能拖；
- **依赖阻塞** → 我出面协调资源或调整方案，不让他自己硬扛；
- **需求变更** → 重新评估范围，**该砍需求就砍需求**，保护的是上线时间和质量底线，而不是"全部做完"。

**延期的处理**（越早越好）：
1. **提前暴露**——我要求同学遇到风险**当天说**，早说有 5 种解法，晚说只有 1 种（加班）；
2. **重新排优先级**——砍非核心需求、分期交付（MVP 先上）；
3. **加资源**——但要算清楚：项目后期加人可能更慢（ Brooks 定律），加人只适合**任务可并行且边界清晰**的情况；
4. **复盘**——延期后一定要回看：**是估算不准、需求变更、依赖阻塞还是技术难度低估**，下次改进估算方式（我习惯用**三点估算 + 参照历史同类任务**）。

**最重要的一条**：**不要靠"大家辛苦一下"解决问题**。加班能救一次，救不了第二次，还会掩盖真正的问题（估算、依赖、优先级）。

### Q55. 你怎么平衡"业务需求快"和"技术质量"？

**回答（岗位第 11 条的核心，要答得出层次）：**

我的原则：**技术服务于业务，但技术债必须显性化和可管理。**

1. **不追求架构完美，追求"可演进"**：我宁愿现在的设计能支撑 6 个月且好改，也不要一个设计 3 年但复杂度高到没人敢动。**为未来留扩展点，但不要为未来写代码**；
2. **用数据谈权衡**：当业务要求两周上线而我认为需要一个月，我不会只说"这样会烂"，而是说清楚：**这套方案能支撑到什么量级、什么时候会出问题、出问题的代价是什么、临时方案改造成正式方案要多久**。让业务方拿着这些信息做决策，决策权在他，但代价要被看见；
3. **技术债记账**：为赶时间做的妥协**必须记入清单，排期偿还**。我见过太多"临时方案"跑了三年成了核心系统；
4. **底线不退让**：有些东西不能妥协——**资金/合规相关的正确性、没有降级手段的外部依赖、没有超时设置的调用、没有监控的核心链路**。这些是稳定性底线，可以砍功能，不能砍这些；
5. **用工程效率还债**：提升交付效率本身就能腾出时间做质量。我做过注解驱动开发提效 40%，这类投入比"加班赶需求"有效得多。

### Q56. 你怎么推进跨部门项目？讲个例子。

**回答（用特惠当日取，这个故事要素最全）：**

特惠当日取是第一次把 B 端阶梯报价应用到 C 端，涉及价格链路全链路改造，跨了产品、前端、支付、运力等多个方。

我做的事：
1. **先摸清全链路**：梳理寄件交易所有涉及价格计算的节点，逐个评估改动成本，形成详细方案再启动，避免做到一半发现漏了环节；
2. **管控需求**：C 端价格展示有很多定制需求，改动成本大的，我拉着前端和产品一起讨论必要性，给出**成本更低的替代方案**（不是简单说"做不了"，而是给选项）；
3. **协调与决策**：线上验单时发现下游域有个标有问题，会影响项目进度。我作为 PM 评估风险后，制定了**在本域消费侧做兼容处理**的方案（不阻塞下游排期），拉会同步老板和相关负责人后，周末紧急发版解决——**这里的关键是：先有方案再拉会，而不是把问题上抛**；
4. **结果**：单量增长 761%、营收增长 452%、净利润增长 215%，获得公司级"小胜即庆"荣誉激励。

**方法论**：**提前识别依赖并书面确认 → 带着方案而不是带着问题沟通 → 决策要留痕 → 风险前置升级**。

## 11. 系统设计大题（高级岗必考，白板设计）

### Q57. 设计一个智能外呼系统（千万级日任务）。

**回答（给结构，不要一上来写代码）：**

**第一步：先澄清需求和约束**（这步本身就加分）
- 日任务量、峰值 QPS、并发通话上限（运营商线路限制，这是硬约束）；
- 是否需要 AI 对话、是否需要转人工、合规要求（外呼时段、频次、DNC 名单、录音留存）；
- 可用性要求（外呼中断的代价）、数据留存周期。

**第二步：架构分层**
```
[运营配置] 任务管理/名单管理/话术与知识库
      ↓
[调度层] 任务分片 → 时间窗调度 → 配额与速率控制(令牌桶) → 优先级队列 → 线路路由
      ↓
[执行层] 呼叫执行器(无状态,水平扩容) → 语音平台(SBC/Kamailio/FreeSWITCH)
      ↓
[AI 编排] ASR / LLM+RAG / TTS 流式管道 (可降级到 IVR 模板)
      ↓
[状态层] 呼叫状态机 + 事件总线(MQ) + 话单(CDR)
      ↓
[后处理] 录音 → 转写 → 质检 / 打标 / 意向分级 → 转人工 / 二次跟进
```

**第三步：核心设计点（挑 4-5 个讲透）**
1. **调度**：见 Q24。核心是"**受限资源的多队列配额调度器**"——线路并发是硬配额，用令牌桶 + 优先级队列 + 时间窗 + 退避重拨。
2. **状态机与可靠性**：每通电话一个状态机（PENDING→DIALING→RINGING→ANSWERED→TALKING→HANGUP→FINISHED），**事件驱动 + 幂等 + 版本号 + 超时兜底 + 主动对账**（这是我治理 ASR 回调超时迁移过来的核心经验，一定要点出来）。
3. **削峰**：任务导入和话单写入走 MQ；质检/转写走离线批处理；**核心链路和非核心链路 MQ 物理隔离**。
4. **降级与容灾**：线路失败率熔断 + 切换备用线路；AI 服务超时降级到模板话术；语音平台多集群，呼叫控制服务无状态可快速重建；**正在通话的会话要有 graceful 处理**（不能因为发布把通话切断）。
5. **存储**：话单按月分库分表 + 冷热分离，分析走 ClickHouse，检索走 ES；配额和席位锁走 Redis。
6. **可观测**：以 **callId** 为业务 trace 标签贯穿全链路；核心指标：接通率、放弃率、AI 解决率、转人工率、端到端延迟、单通成本。

**第四步：讲风险与演进**（这步是高级工程师区别于中级的地方）
- 一期先做**单线路 + 固定速率 + 模板 IVR**，验证链路；二期上预测式调度和多线路路由；三期上 AI 对话和转人工；
- 最大的风险是**合规**（频次、时段、名单）和**成本**（线路费 + AI 调用费），所以系统一开始就要有**配额、预算、频次控制**和**完整的审计留痕**。

### Q58. 设计一个"通话中实时辅助坐席"的功能。

**回答：**

**功能**：坐席通话时，实时显示 ASR 转写文本 + **实时话术推荐** + **合规风险提醒** + 客户画像。

**链路**：媒体服务器把坐席/客户双轨音频 → 实时送 ASR（流式，双轨分开送，天然解决说话人分离）→ 文本流 → （a）推给坐席工作台显示（WebSocket）；（b）送**意图/情绪识别**（小模型，快）；（c）命中关键词或风险规则 → **实时弹屏提醒**；（d）检索知识库（RAG）→ 推荐话术 top3。

**延迟要求**：转写显示 < 1s，话术推荐 < 2s（用向量召回 + 重排，且只对**客户说完一句**后触发，不是每个字都触发）。

**工程要点**：
- **触发时机**：在**客户句末**触发推荐（VAD + 断句），否则频繁刷新坐席没法看；
- **幂等与去重**：同一句话只推荐一次，推荐结果缓存；
- **降级**：AI 服务不可用时不显示推荐（坐席流程不受影响），**绝不能因为辅助功能挂了导致坐席无法工作**；
- **度量**：**采纳率**（坐席是否点击/使用了推荐话术）、推荐后通话时长和成单率变化，做 A/B 验证；
- **隔离**：这个链路是"锦上添花"，必须**独立的资源池和线程池**，与主呼叫链路隔离（对应故障隔离）。

### Q59. 设计一个"客户号码名单管理"系统（千万级名单，去重、分群、频控）。

**回答：**

- **存储**：名单主数据按 `客户ID/手机号哈希` 分库分表（MySQL），或直接用**宽表存储**（Tablestore/Lindorm/HBase，我实际用过）承载千万到亿级，主键是手机号/客户 ID；分析维度同步到 ClickHouse。
- **去重**：导入时按**手机号归一化**（去空格、去 +86、去分隔符）+ **哈希分片并行去重** + **布隆过滤器**快速判重 + DB 唯一索引兜底；跨批次去重（新导入的名单和历史名单、黑名单去重）。
- **分群（圈人）**：标签体系（静态标签 + 行为标签），离线跑批生成人群包（bitmap/roaring bitmap 存人群，交集并集运算快），人群包 ID 关联到外呼任务。
- **频控**：Redis 记录 `手机号 → 最近呼叫时间/次数`，用 ZSet 做**滑动窗口频次控制**（日/周/月上限 + 冷却期），**频控判断必须在放号前的最后一道关**，且要原子（Lua 脚本）。
- **合规**：DNC/黑名单布隆过滤器前置过滤；外呼时段按号码归属地时区判断；**所有过滤都要留痕**（为什么这个号没被呼出），便于审计和解释。
- **导入**：大文件导入走**分片上传 + 异步解析 + 分批入库 + 进度可查 + 失败可重试 + 可回滚**，导入过程不能影响在线放号。

### Q60. 如何设计一个高并发的实时计费/话单系统？

**回答（直接复用支付经验，这是你的强项迁移）：**

- **话单不实时算钱**：通话中只记录**关键事件**（接通时间、挂断时间、挂断方），通话结束后异步计费；**实时性要求高的是"配额预扣"**（类似支付的预授权），而不是最终计费。
- **配额预扣**：发起呼叫前原子扣减账户余额/套餐额度（Redis Lua 或 DB 条件更新 `where balance >= cost`），通话结束后按实际时长**多退少补**，并生成流水。这是我在支付系统的标准做法。
- **幂等**：每通电话的计费以 **callId 为唯一键**，重复事件不重复计费；所有扣减操作必须**幂等 + 可重放**。
- **不丢单**：话单先落库（本地消息表）再发 MQ，异步计费失败进重试队列和死信，**必须有对账**——每日与运营商的话单对账（这正是支付对账的翻版），差异自动补偿 + 人工兜底。
- **写性能**：话单是高频写入 → 批量写入 + MQ 削峰 + 分库分表（按时间 + 客户）。
- **准确性**：金额用**整数分**存储，绝不用浮点数；时长和费率规则要有版本（费率变更不能影响历史话单）。

> **加分点**：明确说"**计费系统的第一原则是可核对，不是快**"。这句话会让面试官觉得你真的做过钱相关的系统。

### 13.1 必须背下来的名词（不懂就会被识破）

## 14. 雷区预警（这些一踩就掉分）

1. **不要吹自己做过 AICC**。被追问"你们外呼的并发上限是多少、用的哪家线路、CPS 多少"会当场穿帮，比承认没做过严重 10 倍。

3. **不要解释为什么最近一份工作只有几个月时显得焦虑**。用"主动选择赛道"的框架讲，并把话题引到对方的平台规划上。
4. **数字要能自证**。"降低 30%"要能说出**口径、对比基线、统计周期**。说不出来就不要讲这个数字。
5. **不要在设计题里一上来谈技术选型**。先澄清需求和约束（量级、合规、可用性），这是高级工程师的标志。
6. **不要说"我觉得这个很简单"**。语音领域的水很深，谦虚反而显得可信（"这块我还没做过，我的理解是……如果我理解错了请您纠正"）。
7. **不要只讲技术不讲业务结果**。这个岗位的第 11、12 条明确要"平衡稳定性、扩展性、交付效率和成本"和"带团队"，所以每个技术点后面最好跟一句业务影响（成本、体验、效率）。
